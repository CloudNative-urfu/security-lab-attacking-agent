# Design

## Context

Архитектура задана картами компонентов/стека и планом интеграций v8 (LangGraph +
LangChain + Temporal + PostgreSQL/pgvector + LiteLLM). Источник истины о данных и
расходах — PostgreSQL; устойчивое выполнение — Temporal; модельный транспорт —
ChatLiteLLM→LiteLLM; агентные графы — LangGraph. v8 прямо говорит, что это выбор
семейств технологий, а совместимость связки проходит отдельные gate (G0–G9), и что
первый вертикальный проход может упрощать bootstrap. Безопасность определяется
харнесом, а не моделью.

## Goals / Non-Goals

**Goals:**
- Чистое, полностью тестируемое доменное ядро, в котором живут все инварианты
  безопасности (допуск, учёт, изоляция, атомарность памяти, lineage чекпоинтов).
- Hexagonal: домен не зависит от конкретной инфраструктуры; внешние системы — порты.
- Рабочий вертикальный срез MVP, запускаемый локально без Temporal/PG/реальной LLM/СС
  (на in-memory/локальных адаптерах), плюс production-путь через PostgreSQL и LiteLLM.
- Детерминированность и идемпотентность по устойчивым идентификаторам.

**Non-Goals:**
- Полный Temporal-workflow и LangGraph-рантайм (требуют запущенных серверов и gate G5);
  вместо этого — порт `ExecutionEngine` с локальным in-process движком и адаптерным
  интерфейсом под Temporal.
- gVisor/containerd sandbox как таковой: поставляется порт `ToolRunner` и локальный
  runner с egress-allowlist и cap подзапросов; усиленная изоляция ОС — отдельный gate G2.
- React-UI: поставляется только API (read-модели + команды); UI вне scope.
- Исследующий агент, snapshot/restore произвольного СС: порты + BLOCKED-поведение.

## Decisions

**D1. Hexagonal / ports-and-adapters.** Домен (`attacking_agent.domain`) — pure Python +
Pydantic, без I/O. Инфраструктура (`attacking_agent.adapters`) реализует порты
(`Protocol`-интерфейсы). Это позволяет тестировать все инварианты на in-memory адаптерах
и менять Temporal/PG/LiteLLM без изменения домена. Альтернатива (прямые вызовы
фреймворков из домена) отвергнута: невозможно тестировать инварианты без инфраструктуры и
нарушается граница v8 «библиотеки внутри компонентов, а не второй рантайм».

**D2. Идентичность и идемпотентность.** Все физические эффекты адресуются стабильными
ID: `op_id` (намерение) → `reservation_id` (резерв бюджета) → `attempt_id` (попытка) →
`charge_id` (расчёт). Новая физическая попытка требует нового `attempt_id` и свежего
permit. Повтор доставки команды с тем же `command_id` и составом возвращает прежний
результат; тот же ID с другим составом — CONFLICT. Это реализуется на уровне домена и
проверяется в журнале/outbox.

**D3. Бюджет — двухфазный с удержанием неизвестности.** `reserve` (атомарно под lock) →
`start` (permit на одну попытку) → `settle` (actual|UNKNOWN). COST_UNKNOWN удерживает
обязательство до сверки; TTL не освобождает резерв. Деньги — `Decimal` с валютой. Жёсткий
лимит превышать нельзя; при фактическом превышении — `BOUND_BROKEN`, остановка выдачи.
Settle идемпотентен по (attempt_id, charge_id).

**D4. Память: один Write-путь, два режима чтения.** Публикует только Writer, атомарно под
branch fence, после повторной проверки сохранённого approval (candidate hash). Controller
не пишет в БД — передаёт проверенного кандидата Writer. Reader отдаёт TASK (текущая задача)
или ANALYSIS (курация), всегда с фильтром scope/branch/version. pgvector/ANN — производный
поиск, не источник истины; при нехватке после фильтрации — точный scoped fallback либо
INCOMPLETE, никогда чужие записи. Events — append-only.

**D5. Разделение владельца выполнения и источника данных.** Движок исполнения (локальный
или Temporal) хранит историю/replay; PostgreSQL хранит предметную истину. Движок получает
ссылки и подтверждения, не становится второй копией ledger. Чистые переходы детерминированы;
модель/СС/БД — I/O-шаги (Activities-подобные).

**D6. Чекпоинт АГ+СС — барьер, затем манифест.** Сначала quiesce/drain (стоп новой выдачи,
сверка незавершённых), затем части пишутся в content-addressed store (hash), затем PG
публикует READY-манифест по expected_head/command_id. Это не 2PC S3+PG. Снимок СС — через
порт `TargetSnapshotAdapter`; при отсутствии snapshot/restore/clone полный чекпоинт —
`BLOCKED`, а не тихий downgrade. Fork наследует префикс истории (lineage), не видит будущее
родителя, имеет независимый scope памяти; расход не откатывается и не создаётся заново.

**D7. LLM Proxy без скрытых повторов.** ChatLiteLLM/LiteLLM создаётся на worker-слое,
retries/fallback явно выключены, фактические отправки считаются. Usage нормализуется в
Decimal-расход и учитывается тем же ledger. Структурированный ответ валидируется Pydantic;
смысл проверяет инициатор, не парсер. Исправление невалидного ответа — отдельная учтённая
операция.

**D8. Политика — deny-by-default, версионно.** `PolicySpec` фиксирует allowlist операций и
адресов и `policy_version`. Проверка адреса выполняется строкой И после DNS/redirect
(порт `AddressResolver`). LLM-предложение не является разрешением.

## Risks / Trade-offs

- [Связка LangGraph+Temporal не испытана (v8 HIGH)] → порт `ExecutionEngine`; MVP на
  локальном детерминированном движке; Temporal-адаптер за gate G5.
- [Локальный `ToolRunner` не даёт изоляции уровня gVisor] → явный egress-allowlist, cap
  подзапросов, deny-by-default; усиление — gate G2; порт не меняется при замене на gVisor.
- [Снимок произвольного СС не гарантирован] → BLOCKED-поведение зафиксировано в спецификации.
- [In-memory адаптеры не доказывают поведение PG/Temporal] → те же доменные контракты
  прогоняются и на PG-адаптере; гонки/fault-injection — отдельные интеграционные тесты (G9).
- [Точные версии пакетов/модель не выбраны] → фиксируются lock-ом на compatibility-gate;
  в коде — абстракции семейств, не хардкод версий.

## Migration Plan

Greenfield. Порядок включения следует G0→G9 из v8: конфиг/ID → память/журнал → политики/
бюджеты/runner → LLM/Reader → Writer/Controller → движок/эпизод → СС → чекпоинт → API →
отказоустойчивость и ревью. MVP закрывает доменные инварианты G0–G5 и API (G8) на
локальных адаптерах; PG-адаптер — production-путь источника истины.

## Open Questions

- Политика финансирования форка (наследование остатка vs. семейный предел) — в v8 помечена
  «требует утверждения»; в MVP реализуется как настраиваемая политика с явным дефолтом
  (наследовать остаток выбранной точки, новые затраты считать отдельно), без автосоздания денег.
