# Design

## Context

Домен за портами (hexagonal). Выносим два stateless-компонента в сетевые сервисы, не меняя
домен: порты `LLMClient` и `ToolRunner` получают HTTP-адаптеры. Источник истины (PG) и
доменная логика (бюджет/журнал/политика) остаются у вызывающего.

## Goals / Non-Goals

**Goals:** реальная сетевая граница для изоляции исполнения инструментов и общего шлюза
модели; контракты портов неизменны; контрактные тесты доказывают эквивалентность.

**Non-Goals:** дробление источника истины (PG остаётся единым); отдельные БД на сервис;
gRPC (пока HTTP/JSON); автоскейл/service mesh.

## Decisions

**D1. Сервисы шарят доменную библиотеку `attacking_agent`.** Монорепо; каждый сервис —
отдельный entrypoint/Dockerfile. Это не дублирует контракты и исключает дрейф.

**D2. LLM-шлюз — чистый транспорт.** Экспонирует `POST /v1/complete` поверх `LLMClient`
(LiteLLM или fake). Бюджет/журнал НЕ в шлюзе — остаются в доменном `LLMProxy` вызывающего.
`HttpLLMClient` реализует `LLMClient`; Decimal-cost передаётся строкой.

**D3. Tool-runner — исполнение по allowlist (анти-RCE).** `POST /v1/run` принимает
идентичность инструмента (module+qualname) и параметры; сервис проверяет allowlist, затем
исполняет через `SubprocessToolRunner` (изоляция/таймаут/cap). Произвольный код вне
allowlist отклоняется. `HttpToolRunner` реализует `ToolRunner`, извлекая идентичность из
`RunRequest.executor`.

**D4. Контрактные тесты in-process.** FastAPI ASGI-транспорт (httpx) без сети/docker
доказывает эквивалентность домена через сетевой адаптер; docker-compose — для реального деплоя.

## Risks / Trade-offs

- [RCE через runner] → строгий allowlist идентичностей; тест на отклонение.
- [Потеря точности Decimal по сети] → cost строкой, реконструкция Decimal; тест точности.
- [Рост сложности деплоя] → оправдан границей безопасности и общим шлюзом; PG-консистентность не трогаем.
