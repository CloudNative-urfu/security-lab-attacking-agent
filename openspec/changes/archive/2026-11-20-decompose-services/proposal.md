# Proposal

## Why

Инварианты консистентности (бюджет, branch-fence) доказаны на реальном PostgreSQL, а
изоляция недоверенного кода и общий доступ к модели — естественные границы для выноса в
отдельные сервисы. Это снимает риск RCE (исполнение инструментов на отдельном хосте с
egress-периметром) и даёт общий stateless-шлюз к моделям (маршрутизация ключей — идея
команды), не ломая доменные контракты: порты получают сетевые адаптеры, домен не меняется.

## What Changes

- Выделяются два сетевых сервиса (деплой из общей доменной библиотеки):
  - **llm-gateway**: транспорт к модели (`LLMClient` по HTTP), маршрутизация провайдеров,
    без скрытых retry; бюджет/журнал остаются у вызывающего (консистентность в PG).
  - **tool-runner**: изолированное исполнение инструментов (`ToolRunner` по HTTP) с
    субпроцессной изоляцией и **allowlist** допустимых инструментов (анти-RCE).
- Доменные порты реализуются сетевыми адаптерами: `HttpLLMClient`, `HttpToolRunner` —
  домен (`LLMProxy`, `Dispatcher`) не меняется.
- Добавляются entrypoints сервисов (`services/…`), Dockerfile'ы и сервисы в docker-compose;
  API и Temporal-воркер — отдельные деплои из того же пакета.

## Capabilities

### New Capabilities

- `service-topology`: сетевая декомпозиция на сервисы с сохранением доменных контрактов и границей безопасности runner.

### Modified Capabilities

- `llm-proxy`: допускается сетевой транспорт модели (`LLMClient` за HTTP-границей).
- `tool-dispatch`: допускается исполнение инструментов удалённым runner с allowlist.

## Impact

- Новый каталог `services/` (llm_gateway, tool_runner, api, worker entrypoints) и адаптеры
  `attacking_agent/adapters/http_*`.
- Новые dev-зависимости для сервисов — переиспользуют `api`/`llm` extras (fastapi, httpx, litellm).
- Контрактные тесты: домен работает идентично через сетевой адаптер (ASGI in-process).
