# Инженерная политика (engineering-policy)

Политика реализации харнеса как часть AI-driven PDLC и Doc-as-Code. Документ —
нормативный: изменение не считается принятым, пока не выполнены ворота и критик-ревью.

## 1. Единые ворота (обязательны локально и в CI)

Одна команда: `scripts/check.sh`. Набор проверок:

| Ворота | Инструмент | Что гарантирует |
|---|---|---|
| Стиль + безопасность | ruff (incl. `S`/flake8-bandit, `PERF`, `PTH`, `C4`, `RET`, `PIE`) | единый стиль, базовые security-антипаттерны |
| Строгая типизация | mypy `--strict` | типобезопасность домена и адаптеров |
| Сканер безопасности | bandit | известные небезопасные конструкции |
| Детект секретов | detect-secrets (по `.secrets.baseline`) | нет новых секретов в коде |
| Аудит зависимостей | pip-audit | нет известных CVE в зависимостях |
| Тесты | pytest | инварианты поведения (включая состязательные) |
| Спецификации | openspec `validate --strict` | спеки и changes согласованы |

Проваленные ворота блокируют принятие. CI (`.forgejo/workflows/ci.yaml`) гоняет тот же набор.

## 2. Процесс изменения (SDD)

1. OpenSpec change: proposal → specs (контракты поведения) → design → tasks.
2. TDD: тест фиксирует инвариант (в т.ч. негативный/состязательный) → реализация.
3. Ворота зелёные.
4. **Критик-ревью** независимым агентом против исходной задачи (см. §3).
5. Устранение подтверждённых findings.
6. Коммит атомарный по capability; архивирование change после приёмки.

## 3. Критик-ревью (guard rails процесса)

Содержательное изменение проходит независимое критик-ревью (агент-критик, напр. code-review)
на diff против задачи. Подтверждённые findings устраняются или явно обосновываются до
принятия. Цель — ловить разрыв «заявлено vs реализовано», гонки, обходы инвариантов и
состязательные дыры (prompt injection, SSRF, обход cap/бюджета).

## 4. Инварианты, которые нельзя ослаблять молча

- Допуск до любой внешней отправки; одна попытка — один permit; повтор — новый attempt.
- Жёсткий бюджет не превышается (в т.ч. между процессами); расход не откатывается форком.
- Недоверенный код исполняется изолированно; недоверенные данные СС не становятся инструкциями.
- Память: один Write-путь под branch-fence; чтение только своей области; pgvector производен.
- Понижение гарантии (напр. отсутствие OS-sandbox или снапшота СС) фиксируется явным статусом
  (`BLOCKED`/документирование), а не тихо.

## 5. Границы честности

Заявления в README и спеках отражают **реально доказанный** уровень (каким движком/адаптером,
в какой среде). Следующие уровни (OS-sandbox сети, Temporal, реальный провайдер/СС) —
отдельные gate, названные явно.
